Laravel Framework GHSA-8h64-cpq2-9h2g — TransformsRequest の JSON 処理による DoS

公開日：2026-11-23（CVE 未採番）· 2026年11月27日 時点。月次レポート：2026年11月レポート。重大度：高（High）（CVSS v3.1 7.5 · AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H）。

最初にお読みください：laravel/framework を 12.74.0+ または 13.38.0+（メモリ最適化まで含む 13.39.0+ を推奨）へ更新してください。Laravel 11.x はセキュリティサポート終了（EOL：2026-03-12）のため修正版は提供されません。本ページに攻撃コードは含みません。

TL;DR 1. 技術メカニズム 2. 影響範囲 3. 確認コマンド 4. 恒久対策・暫定対策 5. 参考情報

TL;DR（かんたん解説）

  • 脆弱性の内容：Laravel の標準ミドルウェア TransformsRequest（TrimStrings・ConvertEmptyStringsToNull の親クラス）の不具合で、ルーティングや認証より前に全リクエストで実行されます。
  • 危険度：未認証の攻撃者が通常サイズ（約 590 KB）の JSON に長い 1 キーと大きな配列を含めて数件並列送信するだけで、数十 GB のメモリ確保と約 30 秒/件の CPU 消費を引き起こし、PHP ワーカーを枯渇させてサービス停止（DoS）に至ります。
  • 対象システム：12.x < 12.74.0、13.x < 13.38.0、および 11.x・10.x 以前（EOL で未修正）のすべての Laravel アプリ。
  • PM／テックリードの対応：composer.lock を確認し、12.74.0+ または 13.39.0+（最低 13.38.0）へ更新してください。11.x はメジャーアップグレード計画が必要です。

1. 概要と技術メカニズム

  • 根本原因：再帰メソッド cleanArray(array $data, $keyPrefix = '') が各要素で $keyPrefix.$key を構築します。PR #62582 の試算では、約 590 KB の JSON（約 295 KB のキー 1 つ＋約 14.7 万要素）で約 43 GB の文字列確保と約 30 秒の CPU 消費が発生します。また未変更配列の毎回代入による copy-on-write 複製や、TrimStrings::transform() が is_string() 前に Str::is() を呼ぶ点も負荷を増大させていました。
  • 修正内容：$maxKeyBytes = 20 * 1024 * 1024（20 MB、Octane 対応のため handle() 開始時に $keyBytes = 0 にリセット）を超過した時点で PostTooLargeException（HTTP 413）を送出します。

4. 恒久対策・暫定対策

方法 1：修正版へのアップグレード（推奨）

  1. laravel/framework の更新：12.74.0+（12.x）または 13.39.0+（13.x。13.38.0 で $maxKeyBytes = 20 MB 制限を導入、13.39.0 で配列 copy-on-write 抑止と TrimStrings 最適化を追加）へ更新します： 
    composer update laravel/framework --with-all-dependencies
composer show laravel/framework | grep versions
composer audit
  2. Laravel 11.x 以前を稼働中の場合：11.x はセキュリティサポート終了済み（2026-03-12）で公式パッチは提供されません。12.74.0+ または 13.39.0+ への移行計画を立てつつ、移行完了までは方法 2 の防御策を適用してください。
  3. $maxKeyBytes の調整（必要な場合）：更新後、TransformsRequest のサブクラスで protected $maxKeyBytes をオーバーライドし、小規模 API では上限をさらに引き下げる（例：2 MB）ことも可能です。
  4. デプロイ・キャッシュ削除・ワーカー再起動： 
    php artisan optimize:clear
# Laravel Octane 利用時（メモリ上のミドルウェアインスタンス更新のため必須）：
php artisan octane:reload
# または PHP-FPM / コンテナを再起動

方法 2：暫定対策・境界防御（即時更新が困難な場合）

公式アドバイザリにアップグレード以外の回避策は記載されていません。TrimStrings / ConvertEmptyStringsToNull を skipWhen() 等で無効化するとアプリ全体の入力正規化（空文字の null 変換や前後空白除去）が変わるため推奨されません。更新までの間は以下の多層防御で DoS リスクを低減してください。

  1. リバースプロキシ／WAF でのボディサイズ制限：nginx / ALB / Cloudflare 側で Content-Length 上限を引き下げます（約 590 KB 程度でも発症し得る点に留意）： 
    # nginx：大容量アップロード不要な API 向けの上限設定例
client_max_body_size 256k;
  2. PHP-FPM のリソース・タイムアウト制限：悪意ある 1 リクエストがワーカープール全体を長時間占有しないよう上限を設定します： 
    ; php-fpm pool (www.conf) および php.ini
request_terminate_timeout = 15s
memory_limit = 256M
  3. EOL 系統（11.x 等）向けの先行ガードミドルウェア：11.x の移行に時間を要する場合、HTTP スタックの最前段（TrimStrings より前）にミドルウェアを配置し、Content-Type: application/json で単一キー長や要素数が過大なリクエストを早期拒否する対策が有効です。
  4. 監視指標：502 Bad Gateway / 504 Gateway Timeout の急増、PHP-FPM の max_children reached、およびワーカーの OOM kill が連続発生していないか監視してください。
