権限の低い DB アカウントだけでサーバー乗っ取りが可能に — PostgreSQL・MySQL・Oracle・ClickHouse の脆弱性

2026年11月19日 時点（Zheng Yu／Depthfirst の研究「Narrow Grants, Wide Engines」11月18日公開、The Hacker News 11月19日、PostgreSQL・MySQL・Oracle の advisory に基づく）。月次レポート：2026年11月レポート。重大度：緊急（Critical）（Oracle Text の CVSS 9.9、および研究者が認証不要と説明する ORDS 経由の連鎖による）。

最初に：(1) ORDS をインターネットに公開しない、Oracle の 2026年10〜11月の更新を適用；(2) PostgreSQL 18.7 / 17.12 / 16.16 / 15.20 / 14.25（本サイトで既に取り上げた 2026-11-12 の同じリリース）および MySQL 26.7.x を 26.7.1 より後の版へ更新；(3) 不要なアカウントから一時テーブル作成権限を剥奪。実環境での悪用は未確認です。本ページに攻撃コードは含みません。

MySQL のバージョン番号について —「26.7」は誤記ではありません： 2026年7月から Oracle は MySQL のバージョンをカレンダー方式 YY.M.P（年.月.パッチ）に変更しました。26.7.0 は 2026年7月リリースの Innovation 版で、MySQL 9.7 が旧方式の最後のため 9.8 は存在しません。8.0 / 8.4 LTS に慣れている方は注意：本脆弱性の対象は Innovation の 26.7 系のみで、8.0、8.4 LTS、9.7 は advisory の対象一覧に含まれていません。バージョン番号だけでは Innovation か LTS かは判別できないため、SELECT VERSION(); とリリースノートで確認してください。出典：Oracle MySQL Blog、Percona。

TL;DR（かんたん解説）

  • 何が起きた？ 研究者 Zheng Yu（Depthfirst）が、ごく狭い権限しかないデータベースアカウント（アプリのテーブルを一切読めない）でも、データベース製品自体のメモリバグを突いてサーバー上でコマンドを実行できることを実証しました。PostgreSQL、MySQL、Oracle、ClickHouse で確認されています。
  • なぜ問題？ 「一時テーブルを作れるだけのアカウントなら無害」と考えがちですが、SQL の権限が決めるのはどのテーブルを読めるかだけで、クエリを処理するコード内のバグは防げません。Oracle については、ORDS（REST／GraphQL）経由でログイン前に到達できる連鎖を研究者が説明しています。
  • 対象は？ 2026-11-12 版に未更新の PostgreSQL、MySQL 26.7.0〜26.7.1、2026年11月の更新未適用の Oracle Database 19c/21c/23ai、ORDS 24.2.0〜26.2.1、ClickHouse（確認済みの修正なし）。
  • PM／管理者がすべきこと： データベースとバージョンの棚卸し、インターネット公開された ORDS を持つ Oracle を最優先に、更新と再起動の計画、共有アカウントやサードパーティ（BI、レポート、連携）のアカウントが一時テーブル権限を持っていないかの確認をエンジニアに依頼してください。

1. 技術概要

  • 核心： SQL の権限はアカウントが触れるテーブル／スキーマを制御するもので、クエリを解析・計画・実行する（メモリ安全でない）C/C++ のコードは制御しません。よくある低い権限（PostgreSQL の既定の TEMPORARY、MySQL／ClickHouse の CREATE TEMPORARY TABLE(S)）で、メモリ破壊バグに到達するオブジェクトの作成や入力の送信ができ、データベースの OS ユーザーとしてコードが実行されます。研究で使われたアカウントはアプリのテーブルを読めませんでした。
  • PostgreSQL（CVE-2026-116331）： min/max 集約の最適化における型混乱。オブジェクト作成者がデータベースを実行する OS ユーザーとして任意コードを実行可能。CVSS 3.0 8.8。Depthfirst によれば、既定の CONNECT ＋ TEMPORARY を持つ通常のログインロールが、自身の一時スキーマ内で必要なオブジェクトを作成できます。
  • MySQL（CVE-2026-101786）： 対象は Innovation の 26.7 系のみ（2026年7月からカレンダー方式 YY.M.P、8.x ではない — ページ冒頭の注記参照）。Server: Optimizer コンポーネントの脆弱性。Oracle の評価は CVSS 3.1 7.2（PR:High）。Depthfirst は 26.7.0 のイメージで、CREATE TEMPORARY TABLES ON *.* のみを持ち既存テーブルを読めないアカウントから RCE に到達しました。
  • Oracle Database – Oracle Text（CVE-2026-114819）： CVSS 3.1 9.9、Oracle の記載では「Create Session」権限が必要。ORDS GraphQL（CVE-2026-91609、CVSS 6.5）と組み合わせ、公開された ORDS エンドポイントに対して用いると、エンジンコードに到達しログイン前にコマンドを実行できると Depthfirst は説明しています。Oracle はどちらも単独では認証不要と評価していません（5 章参照）。
  • ClickHouse（CVE なし）： RowBinary 形式の文字列長読み取りにおける整数オーバーフローによる範囲外書き込み。ユーザーが format_binary_max_string_size = 0（0 = 無制限、既定は 1 GiB）を設定すると到達可能。*.* に対する CREATE TEMPORARY TABLE が必要。Depthfirst は 26.7.5.10（stable）でシェルを取得。advisory・確認済みの修正はありません。
  • 悪用状況： 実環境での悪用は未確認。完全な PoC は公開されていません（一部抜粋・簡略化した環境のみ）。

3. 確認方法

バージョンと、一時テーブル作成権限を持つアカウントを確認します。以下はいずれも参照のみのコマンドです。

PostgreSQL

SELECT version();
SHOW server_version;
-- PUBLIC（全ロール）が現在の DB で TEMPORARY を持っているか
SELECT has_database_privilege('public', current_database(), 'TEMPORARY');
-- datacl が NULL = 既定の権限（PUBLIC に CONNECT + TEMPORARY）
SELECT datname, datacl FROM pg_database;

MySQL

SELECT VERSION();
-- グローバルに CREATE TEMPORARY TABLES を持つアカウント
SELECT GRANTEE, PRIVILEGE_TYPE FROM information_schema.USER_PRIVILEGES
 WHERE PRIVILEGE_TYPE = 'CREATE TEMPORARY TABLES';
-- スキーマ単位
SELECT GRANTEE, TABLE_SCHEMA FROM information_schema.SCHEMA_PRIVILEGES
 WHERE PRIVILEGE_TYPE = 'CREATE TEMPORARY TABLES';

Oracle Database / ORDS

# SQL*Plus / SQLcl で
SELECT banner_full FROM v$version;
# ORDS のバージョン（ORDS を実行しているホストで）
ords --version

あわせて、ORDS（REST／GraphQL）のエンドポイントがインターネットから到達可能か（ALB、リバースプロキシ、セキュリティグループ）を確認してください。

ClickHouse

SELECT version();
SHOW GRANTS FOR <user>;
-- CREATE TEMPORARY TABLE を持つユーザー／ロール
SELECT user_name, role_name, access_type, database
  FROM system.grants WHERE access_type = 'CREATE TEMPORARY TABLE';
-- 現在の設定値（0 = 無制限）
SELECT name, value, changed FROM system.settings
 WHERE name = 'format_binary_max_string_size';

マネージドサービス（Amazon RDS / Aurora、Cloud SQL など）：コンソールでエンジンのマイナーバージョンと、プロバイダーのメンテナンス枠を確認してください。

4. 恒久対策と暫定策

方法 1：修正の適用（推奨）

  1. Oracle Database： 19c / 21c / 23ai に 2026年11月の更新（CSPU）を適用。ORDS： 26.2.1 より後の最新版へ更新（2026-10-20 CPU）。ORDS ＋ Oracle Text の連鎖はログイン不要と説明されているため、ORDS が外部から到達可能なら最優先です。
  2. PostgreSQL： マイナーバージョンを 18.7 / 17.12 / 16.16 / 15.20 / 14.25 に更新し、サーバーを再起動。PostgreSQL 14 は EOL のため、ブランチ移行を計画してください。詳細手順（バックアップ、REINDEX など）は PostgreSQL 2026年11月アップデートのページを参照。
  3. MySQL Server / Cluster 26.7.0〜26.7.1： 2026年10月 CPU の 26.7.1 より後のリリースへ更新し再起動（advisory に具体的なバージョン番号の記載はないため、リリースノートで確認。Oracle の案内では Innovation 系の特別パッチは 26.7.0.x 形式になり得るため、「26.7.1」という文字列だけで判定しないこと）。8.0 / 8.4 LTS / 9.7 を使用している場合は本 CVE の対象外です。
  4. ClickHouse： 確認済みの修正はありません。方法 2 の緩和策を適用し、ClickHouse の changelog／GitHub Security Advisories を注視してください。
  5. マネージドサービス： プロバイダーがメンテナンス枠で適用します。エンジンのマイナーバージョンを確認し、新しい版が出たら能動的に適用してください。各プロバイダーの対応状況は未確認です。

方法 2：暫定策（攻撃面の縮小）

重要： PostgreSQL の advisory に回避策の記載はありません。以下は Depthfirst の推奨に基づくもので、攻撃面を減らすだけであり、修正の代わりにはなりません。一時テーブル権限の剥奪は Oracle／ORDS の経路には効果がありません。

  1. Oracle／ORDS： ORDS（REST／GraphQL）をインターネットに公開せず、入口で VPN／IP 許可リスト／SSO の配下に置きます。
  2. PostgreSQL — PUBLIC の既定の TEMPORARY を剥奪し、本当に必要なロールにのみ再付与。注意：一時テーブル（CREATE TEMP TABLE）を使うアプリ、ORM、マイグレーション、BI ツールは再付与しないと失敗します。先にステージングで確認してください。 
    REVOKE TEMPORARY ON DATABASE <db> FROM PUBLIC;
GRANT TEMPORARY ON DATABASE <db> TO <app_role>;  -- 必要なロールのみ
  3. MySQL — 不要なアカウントから CREATE TEMPORARY TABLES を剥奪（特にレポート閲覧用やサードパーティ連携用のアカウント）： 
    REVOKE CREATE TEMPORARY TABLES ON *.* FROM '<user>'@'<host>';
  4. ClickHouse — 設定プロファイルの制約でユーザーが format_binary_max_string_size を変更できないようにし、CREATE TEMPORARY TABLE を制限： 
    <profiles>
  <default>
    <constraints>
      <format_binary_max_string_size>
        <readonly/>   <!-- または <min>1</min> で 0 を禁止 -->
      </format_binary_max_string_size>
    </constraints>
  </default>
</profiles>
    REVOKE CREATE TEMPORARY TABLE ON *.* FROM <user>;
  5. アカウントの見直し： 共有アカウント、サードパーティに発行したアカウント、社内ツールの接続文字列にあるアカウント。「低権限なら安全」という前提はエンジン内のバグには通用しません。
  6. 被害の限定： データベースは専用の最小権限 OS ユーザーで実行し、不要なら DB サーバーからインターネットへの外向き通信を禁止。データベースプロセスの異常なクラッシュ／再起動を監視。

優先順位：(1) インターネット公開された ORDS を持つ Oracle、(2) 外部や多数の人が持つ低権限アカウントがある DB（マルチテナント、BI、連携）、(3) その他の影響を受ける PostgreSQL／MySQL、(4) ClickHouse（暫定策を適用し修正を注視）、(5) 開発／ステージング環境。

5. 情報の信頼性

  • Oracle — ベンダーと研究者の見解が異なる： Oracle は CVE-2026-114819 を「Create Session」が必要、CVE-2026-91609 を PR:L とし、いずれも「認証なしでリモート悪用可能：No」としています。Depthfirst は、公開された ORDS エンドポイント経由で両者を連鎖させるとログイン前に実行できると説明しています。本ページは両方の見解を併記し、インターネット公開された ORDS を最優先としています。
  • MySQL — ベンダーと研究者の見解が異なる： Oracle の評価は PR:High（7.2）ですが、Depthfirst によれば CREATE TEMPORARY TABLES ON *.* のみで足り、ベンダー評価よりはるかに狭い権限です。
  • 悪用状況： 実環境での悪用は未確認、完全な PoC は非公開。The Hacker News は完全な攻撃チェーンを独自に再現していません。
  • 未確認： MySQL と ORDS の具体的な修正バージョン番号（advisory に記載なし。26.7 系のパッチ番号が 26.7.1 か 26.7.0.x かは Oracle の資料間で不一致）、ClickHouse の修正／advisory、各マネージドサービスの対応状況。
  • 混同注意： CVE-2026-6460 は同じ 2026-11-12 のリリースで修正された PostgreSQL の別の型混乱の脆弱性です。
