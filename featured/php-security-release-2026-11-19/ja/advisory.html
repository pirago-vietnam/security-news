PHP の CRITICAL 級セキュリティ修正版（2026-11-19）：8.5.13 / 8.4.28 / 8.3.37 / 8.2.36 で 17 件の CVE を修正

2026-11-19 00:30（JST, UTC+9、日付は 11/20）更新：PHP が修正版を公開済みです（GitHub アドバイザリは 14:05〜14:08 UTC に公開）。月次レポート：2026年11月レポート。重大度：緊急（Critical）、CVSS 4.0 最大 9.2。

対応：PHP を 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13（または 8.6.0）へ更新し、PHP-FPM／Apache の再起動とイメージ再ビルドを実施してください。8.1 以前は修正版なし。すぐに更新できない場合は session.upload_progress.enabled を無効化（CVE-2026-115560 のみの暫定策で、他の脆弱性は防げません）。実環境での悪用を報告した情報源は確認できていません。

1. リリース概要

  • バージョン：PHP 8.5.13、8.4.28、8.3.37、8.2.36（セキュリティリリース）と 8.6.0（GA、同日公開）。PHP.net アーカイブによる。GitHub にも対応タグがあります。
  • 規模：GHSA 17 件、うち CVSS 9.2（Critical）が 7 件：エンジン／ext/date／ext/session のメモリ破壊（UAF）4 件、ext/session のデシリアライズ／RCE 2 件、PHP-FPM のリクエストスマグリング 1 件。High 4 件、Moderate 6 件。PHP.net は CRITICAL でも非デフォルト設定または稀な構成が必要としています。
  • CVE-2026-115560 は 10/23 のアドバイザリで「次のリリースで詳細公開」とされていた件です。cve.org：CNA は PHP Group、CVSS 4.0 9.2、CWE-20 / CWE-502。10 月のリリース（8.5.12 など）では修正されていません。
  • IPA による事前注意喚起（2026-11-19）：公開予定時刻（JST 23:00〜23:30 頃）に先立ち、IPA が事前準備を呼びかけました。公開時点で IPA は悪用攻撃を確認していません。10 月の PHP2Shell（CVE-2026-109618 / 109619）の予告時とは異なり「非デフォルト設定または一般的ではないセットアップ」が対象とされているものの、公開後きわめて短時間で悪用される可能性や、サポート終了版の稼働が依然見られる点に注意を促しています。

3. CVE ごとの確認方法と暫定緩和策

以下のコマンドは読み取り専用の目安です。「該当なし」の結果が安全を保証するものではなく、CLI の php は FPM／Apache と別の php.ini を使う場合があります（実際の設定は php-fpm -tt や社内限定の phpinfo() で確認）。/etc/php*、/etc/nginx などのパスはディストリにより異なります。暫定策は攻撃面を減らすだけで、根本対策は 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13（または 8.6.0） への更新と再起動です。

共通の確認（バージョン・設定・拡張）

php -v                       # CLI
php-fpm -v                   # (または php-fpm8.x -v) FPM
docker run --rm <image> php -v
php-fpm -tt 2>&1 | grep -E "catch_workers_output|status_path|php_(admin_)?value"   # FPM の実効設定
php -m | grep -iE "soap|dom|phar|session"   # 読み込み済み拡張

CVE-2026-115560 (session upload progress)

upload_progress.enabled=1 かつセッションストアを共有するアプリ間で serialize_handler が異なる場合にリスクがあります。

確認コマンド

php -r 'echo ini_get("session.upload_progress.enabled"), PHP_EOL, ini_get("session.serialize_handler"), PHP_EOL;'
grep -RInE "ini_set\(\s*['\"]session\.serialize_handler|session_set_save_handler" --include=*.php .
grep -RInE "session\.serialize_handler" /etc/php* /usr/local/etc/php* 2>/dev/null

暫定緩和策

  • php.ini／FPM プールで upload progress を無効化（ini_set() や .user.ini は使わない）し、ワーカーを再起動。
  • セッションストアを共有する全アプリ／プール／vhost／CLI で session.serialize_handler を統一し、実行時の ini_set('session.serialize_handler') を廃止。
  • アプリごとにセッションストア（プレフィックス／DB）を分離。
session.upload_progress.enabled = 0
; PHP-FPM pool:
php_admin_value[session.upload_progress.enabled] = 0

CVE-2026-129496 (ext/date UAF)

悪用には警告がファイル形式の error_log に書き込まれることが前提です。

確認コマンド

php -r 'foreach(["error_log","log_errors","display_errors","max_input_vars"] as $k) echo $k,"=",ini_get($k),PHP_EOL;'
php-fpm -tt 2>&1 | grep -E "error_log|max_input_vars"

暫定緩和策

  • error_log をファイルではなく syslog または stderr（コンテナ）に変更。display_errors=0 を維持。
  • リバースプロキシ／WAF で過大なパラメータ数（max_input_vars 付近以上）のリクエストを遮断し、ボディ／クエリサイズを制限。
  • 攻撃面を減らすだけで脆弱性は残るため、バージョン更新は必須。
error_log = syslog
log_errors = 1
display_errors = 0

CVE-2026-129289 (PHP-FPM request smuggling)

フロントエンドが FPM へのバックエンド接続を維持し、かつ php://input を最後まで読まないコードがある場合にリスクがあります。

確認コマンド

grep -RInE "fastcgi_keep_conn" /etc/nginx            # on = リスクあり
grep -RInE "enablereuse" /etc/apache2 /etc/httpd 2>/dev/null   # on = リスクあり
grep -RInE "fcgi|fastcgi" /etc/haproxy 2>/dev/null
grep -RIn "php://input" --include=*.php .

暫定緩和策

  • nginx: fastcgi_keep_conn off;（デフォルト）にして reload。
  • Apache mod_proxy_fcgi: enablereuse=off。HAProxy: FastCGI 接続の再利用を無効化。
  • php://input を使う場合はボディを最後まで読む（stream_get_contents）か、$_POST／フレームワークのリクエストを使用。
  • FPM を信頼できるネットワーク外に公開しない（unix ソケット／127.0.0.1 のみ）。
# nginx
fastcgi_keep_conn off;
# Apache
ProxyPass "/" "fcgi://127.0.0.1:9000/" enablereuse=off

CVE-2026-126714 (セッションファイルの部分上書き)

files ハンドラ（デフォルト）のみ影響。マルチスレッド PHP（ZTS）でリスクが高まります。

確認コマンド

php -r 'echo ini_get("session.save_handler"), PHP_EOL, ini_get("session.save_path"), PHP_EOL, ini_get("memory_limit"), PHP_EOL;'
php -i | grep -E "Thread Safety|Server API"        # ZTS=enabled はリスク高
grep -RInE "unserialize\(" --include=*.php . | grep -v vendor/ | head

暫定緩和策

  • session.save_handler を Redis／Memcached／DB に変更（他のハンドラはこのファイル書き込みの欠陥なし）。事前に十分テスト。
  • ZTS ではなく NTS（FPM／prefork）を使い、memory_limit を十分に確保して途中中断を避ける。
  • 生のユーザーデータをセッションに入れない。ガジェットチェーンを点検（composer audit、Guzzle／Monolog 等の更新）。
session.save_handler = redis
session.save_path = "tcp://127.0.0.1:6379"

CVE-2026-129481 (セッション shutdown 時の UAF)

8.3 以降のみ影響。独自ストリームラッパーの stream_close() など、セッション終了処理で fatal error が起きる場合。

確認コマンド

php -r 'echo PHP_VERSION, PHP_EOL;'      # 8.3 以降のみ
grep -RInE "stream_wrapper_register|session_set_save_handler|SessionHandlerInterface" --include=*.php . | grep -v vendor/

暫定緩和策

  • 自作のストリームラッパー／セッションハンドラを点検し、close()／stream_close() 内のエラーを捕捉して fatal error を防ぐ。
  • 自作ハンドラを標準ハンドラ（files／redis）に一時的に置き換える。
  • この欠陥を無効化する設定はなく、バージョン更新が主な対策です。

CVE-2026-129474 (Engine UAF（__call のバックトレース）)

8.5 のみ影響。fatal_error_backtraces=1 かつ zend.exception_ignore_args=0 が前提。

確認コマンド

php -r 'echo PHP_VERSION, PHP_EOL, "fatal_error_backtraces=", ini_get("fatal_error_backtraces"), PHP_EOL, "exception_ignore_args=", ini_get("zend.exception_ignore_args"), PHP_EOL;'
php-fpm -tt 2>&1 | grep -E "exception_ignore_args|fatal_error_backtraces"

暫定緩和策

  • zend.exception_ignore_args=1 に設定（php.ini-production の値）。
  • fatal_error_backtraces=0 に設定（8.5 のデフォルトは 1）。
  • 本番で php.ini-development を使わない。
zend.exception_ignore_args = 1
fatal_error_backtraces = 0

CVE-2026-129182 (Engine UAF（last_fatal_error_backtrace）)

8.5 のみ影響。パス別の特殊設定（max_memory_limit、zlib.output_compression／ob_gzhandler）と PHP_VALUE／PHP_ADMIN_VALUE またはディレクトリ別設定の併用が前提。

確認コマンド

php -r 'echo PHP_VERSION, PHP_EOL;'      # 8.5 のみ
grep -RInE "PHP_VALUE|PHP_ADMIN_VALUE|php_value|php_admin_value|fastcgi_param +PHP_" /etc/nginx /etc/apache2 /etc/httpd /etc/php* /usr/local/etc/php* 2>/dev/null
find . -name .htaccess -o -name .user.ini | xargs grep -nE "max_memory_limit|zlib\.output_compression" 2>/dev/null
grep -RInE "ob_gzhandler|max_memory_limit" --include=*.php . | grep -v vendor/

暫定緩和策

  • パス別の max_memory_limit／zlib.output_compression／ob_gzhandler 設定をやめ、グローバル値に統一。
  • Web サーバーから動的に PHP_VALUE／PHP_ADMIN_VALUE を渡さない。.htaccess を制限（AllowOverride None）。
  • さらに fatal_error_backtraces=0 で範囲を絞る。
fatal_error_backtraces = 0
; Apache
AllowOverride None

CVE-2026-129291 (PHP-FPM epoll → マスターへの権限昇格)

ローカル脆弱性：ワーカー内で PHP コードを実行できることが前提。公式 PHP-FPM Docker イメージは docker.conf で catch_workers_output を有効化しています。

確認コマンド

php-fpm -tt 2>&1 | grep -E "catch_workers_output|^\[.*pool|user =|events.mechanism"
grep -RIn "catch_workers_output" /etc/php* /usr/local/etc/php-fpm.d 2>/dev/null
ps -o user,pid,cmd -C php-fpm,php-fpm8.5     # master の実行ユーザー

暫定緩和策

  • プールで catch_workers_output = no に設定（ワーカーの stdout／stderr は失われるため、アプリ側の error_log で記録）。
  • コンテナ：可能なら FPM マスターを非 root ユーザーで実行。
  • アプリごとにプール／コンテナを分離し、信頼できないコードには disable_functions を適用して最初のコード実行を困難にする。
; /usr/local/etc/php-fpm.d/zz-hardening.conf
[www]
catch_workers_output = no

CVE-2026-127960 (HTTP ラッパーの折り返しヘッダー DoS)

アプリが信頼できない URL を PHP の HTTP(S) ストリームラッパーで取得する場合にリスクがあります。

確認コマンド

php -r 'echo "allow_url_fopen=", ini_get("allow_url_fopen"), PHP_EOL, "default_socket_timeout=", ini_get("default_socket_timeout"), PHP_EOL;'
grep -RInE "(file_get_contents|fopen|file|get_headers|copy)\(\s*['\"\$]?https?" --include=*.php . | grep -v vendor/ | head -30
php-fpm -tt 2>&1 | grep -E "pm.max_children|request_terminate_timeout"

暫定緩和策

  • 不要なら allow_url_fopen=0。外部リクエストは cURL／Guzzle へ移行。
  • default_socket_timeout を短くし、FPM プールに request_terminate_timeout を設定してワーカーの占有を防ぐ。
  • 取得先をホストのホワイトリストに限定し、タイムアウト付きの egress プロキシを使用。
allow_url_fopen = 0
default_socket_timeout = 5
; FPM pool
request_terminate_timeout = 30s

CVE-2026-128064 (大文字 HTTPS/FTPS が平文送信)

アプリが大文字小文字を区別せずスキームを検証し、そのままストリームラッパーで開く場合（HTTPS://、FTPS://）。

確認コマンド

grep -RInE "stripos\(.*https?://|strpos\(.*https?://|str_starts_with\(.*https?|FILTER_VALIDATE_URL" --include=*.php . | grep -v vendor/
grep -RInE "(file_get_contents|fopen|copy)\(\s*\$" --include=*.php . | grep -v vendor/ | head -30

暫定緩和策

  • URL を開く前にスキームを小文字へ正規化してホワイトリスト検証（コード参照）。
  • ストリームラッパーの代わりに cURL／Guzzle を使用（CURLOPT_PROTOCOLS を HTTPS のみに）。
  • 機密性の高いサービスでは egress ファイアウォール／プロキシで外向き 80／21 を遮断。
$scheme = strtolower((string) parse_url($url, PHP_URL_SCHEME));
if ($scheme !== 'https') { throw new InvalidArgumentException('https only'); }
// 正規化した URL のみ渡す: 'https' . substr($url, 5)

CVE-2026-128090 (phar: OpenSSL 署名のバイパス)

OpenSSL 署名付き phar を読み込み、攻撃者が phar を差し替えられる場合にリスクがあります。

確認コマンド

php -r 'var_dump(extension_loaded("phar"), ini_get("phar.require_hash"), ini_get("phar.readonly"));'
grep -RInE "new +Phar|Phar::|phar://" --include=*.php . | grep -v vendor/
find / -name "*.phar" -not -path "*/proc/*" 2>/dev/null | head -50
find / -name "*.phar.pubkey" 2>/dev/null

暫定緩和策

  • 読み込み前に、固定した SHA-256／GPG など外部手段で phar の完全性を検証（埋め込み署名のみに頼らない）。
  • phar と .pubkey を root 所有の読み取り専用にし、書き込み可能なディレクトリ外に配置。そこへのアップロードを遮断。
  • Web アプリで phar を使わないなら FPM の phar 拡張を無効化（Composer 利用の CLI は維持）。
sha256sum tool.phar            # 信頼できる経路で公開された値と比較
chmod 0444 tool.phar tool.phar.pubkey && chown root: tool.phar tool.phar.pubkey

CVE-2026-129538 (php-cgi PATH_INFO OOB)

php-cgi（CGI／FastCGI）で cgi.fix_pathinfo=1 の場合のみ。PHP-FPM と mod_php は影響なし。

確認コマンド

which php-cgi; php-cgi -v
ps aux | grep -E "[p]hp-cgi"
php-cgi -i | grep -E "cgi.fix_pathinfo|Server API"
grep -RInE "php-cgi|AddHandler.*cgi|SetHandler.*cgi|fastcgi_pass +unix:.*cgi" /etc/nginx /etc/apache2 /etc/httpd /etc/lighttpd 2>/dev/null

暫定緩和策

  • php-cgi から PHP-FPM（または mod_php）へ移行。
  • php-cgi を維持する場合：cgi.fix_pathinfo=0（ルーティングが PATH_INFO に依存しないか確認）とし、存在する .php のみ転送（try_files $uri =404）。
  • WAF で .php/ の後に異常な PATH_INFO を含む URL を遮断。
cgi.fix_pathinfo = 0
# nginx
location ~ \.php$ { try_files $uri =404; fastcgi_pass unix:/run/php/php-fpm.sock; include fastcgi_params; }

CVE-2026-129506 (ext/soap DTD エンティティ UAF)

攻撃者制御の XML／WSDL を ext/soap で処理する場合（認証前にパースすると認証は防御にならない）。

確認コマンド

php -m | grep -i soap
php-fpm -m 2>/dev/null | grep -i soap
grep -RInE "new +SoapServer|new +SoapClient|soap_version" --include=*.php . | grep -v vendor/
grep -RInE "soap|\.wsdl|\.asmx" /var/log/nginx/access.log 2>/dev/null | tail

暫定緩和策

  • ext/soap を使わないなら無効化（phpdismod soap または extension=soap を削除）し、FPM を再起動。
  • Web サーバーで SOAP エンドポイントを IP／VPN／mTLS で制限。
  • WAF／プロキシで <!DOCTYPE／<!ENTITY を含む SOAP ボディを遮断。
  • SoapClient は信頼できる WSDL／エンドポイントのみ。外部 URL ではなくローカルに保存した WSDL を使用。
sudo phpdismod soap && sudo systemctl restart php8.x-fpm

CVE-2026-15353 (ext/soap arraySize ヒープ漏えい)

CVE-2026-129506 と同じ ext/soap。SoapClient が悪意あるサーバーの応答を受ける場合も該当。

確認コマンド

php -m | grep -i soap
grep -RInE "new +SoapServer|new +SoapClient" --include=*.php . | grep -v vendor/

暫定緩和策

  • ext/soap を使わないなら無効化。SOAP エンドポイントのアクセス制限は CVE-2026-129506 と同様。
  • デコードした SOAP 配列をそのままクライアントへのレスポンスに出さない。
  • SoapClient は信頼できるサーバーのみに接続し、TLS を検証。

CVE-2026-129501 (ext/dom double free)

8.4 以降のみ。新 DOM API（Dom\XMLDocument、Dom\HTMLDocument）で信頼できない入力をパースし saveXml() を呼ぶ場合。

確認コマンド

php -r 'echo PHP_VERSION, PHP_EOL;'      # 8.4 以降のみ
grep -RInE "Dom\\\\(XMLDocument|HTMLDocument)|->saveXml\(" --include=*.php . | grep -v vendor/

暫定緩和策

  • 信頼できない入力には Dom\XMLDocument／Dom\HTMLDocument ではなく従来の DOMDocument を使用。検証のうえ saveXml() を saveHtml()／C14N() に置き換える。
  • 入力サイズを制限し、pm.max_requests を有限にしてクラッシュ後に回復（影響は DoS）。

CVE-2026-129438 (ext/uri 約 2 GiB のシリアライズ)

8.5 以降のみ。約 2 GiB の URI を Uri\Rfc3986\Uri に渡す場合。parse_url() と Uri\WhatWg\Url は影響なし。

確認コマンド

php -r 'echo PHP_VERSION, PHP_EOL;'      # 8.5 以降のみ
grep -RInE "Uri\\\\Rfc3986\\\\Uri" --include=*.php . | grep -v vendor/
grep -RInE "large_client_header_buffers|client_max_body_size|LimitRequestLine" /etc/nginx /etc/apache2 /etc/httpd 2>/dev/null

暫定緩和策

  • Uri\Rfc3986\Uri を作る前に URI／入力の長さを制限（例：strlen($uri) <= 8192）。
  • nginx（large_client_header_buffers、client_max_body_size）または Apache（LimitRequestLine）でリクエストライン／ヘッダー／ボディを制限。
  • 信頼できない入力には一時的に parse_url() または Uri\WhatWg\Url を使用。
# nginx
large_client_header_buffers 4 8k;
client_max_body_size 10m;

CVE-2026-129292 (PHP-FPM status ページ XSS)

status ページが有効で、HTML 版を開く人／ツールがある場合。アクセス制限だけでは不十分（他のアプリ経由で payload を仕込めるため）。

確認コマンド

grep -RInE "pm\.status_(path|listen)" /etc/php* /usr/local/etc/php-fpm.d 2>/dev/null
grep -RInE "pm_status|fastcgi_pass.*status|location.*status" /etc/nginx /etc/apache2 /etc/httpd 2>/dev/null
curl -si http://127.0.0.1/status | head -5     # 200 + HTML = 有効

暫定緩和策

  • 未使用なら status ページを無効化：プールの pm.status_path をコメントアウトし FPM を reload。
  • 監視が必要なら ?json（または ?openmetrics）のみ使用し、ブラウザで HTML 版を開かない。Web サーバーで ?html を遮断。
  • status の location に Content-Security-Policy: default-src 'none' と X-Content-Type-Options: nosniff を付与し、アプリと Cookie を共有しない専用オリジンに配置。
; php-fpm pool
;pm.status_path = /status
# nginx
location = /status { allow 127.0.0.1; deny all; add_header Content-Security-Policy "default-src 'none'" always; add_header X-Content-Type-Options nosniff always; include fastcgi_params; fastcgi_pass unix:/run/php/php-fpm.sock; }

CVE-2026-129481 のように設定で完全に無効化できない脆弱性もあり、根本対策はバージョン更新のみです。

4. 対応事項

  1. インターネット公開度で優先順位付け：公開 PHP-FPM／mod_php、multipart アップロードを受けるアプリ、セッションストア（Redis・ファイル・DB）を共有するアプリ。
  2. バージョン更新：8.2.36 / 8.3.37 / 8.4.28 / 8.5.13（準備ができていれば 8.6.0）。公式 Docker イメージ php:* にも新タグ（8.5.13-fpm、8.4.28-fpm、8.3.37-fpm、8.2.36-fpm、8.6.0-fpm）が公開済みです。再 pull して php -v を確認してください。
  3. 再起動必須：reload では旧バージョンのワーカーが残ります。PHP-FPM／Apache を再起動し、イメージ再ビルドと再デプロイを行ってください。
  4. ディストリ／ホスティング：Debian は修正版を公開済みです（bookworm：8.2.36-1~deb12u1 / DLA-4916-1、trixie：8.4.28-1~deb13u1 / DSA-6641-1）。Red Hat（RHEL 7/8/9/10）は CVE-2026-115560 について Affected（修正 Errata 未公開）となっています。その他のディストリ（Ubuntu・Amazon Linux など）は本家より遅れる場合があるため、信頼できるビルドを使うか、待つ間は緩和策を適用してください。
  5. サポート終了ブランチ（8.1 以前）：更新計画を立て、当面はアクセス制限、upload progress 無効化、WAF を適用。
  6. PHP 利用状況の棚卸しと製品・機器内部の組み込み（IPA 推奨）：自組織で開発・運用しているプログラムの棚卸しに加え、PHP はソフトウェア製品やネットワーク機器の内部で利用されている場合があります（利用者側から直接把握できないケースあり）。マニュアルや開発元・提供元のセキュリティ情報を確認し、PHP 利用が判明している製品の今後の情報に注視してください。
  7. 更新後：PHP-FPM のエラーログと不審なセッションを確認し、注入の疑いがあればセッションを失効させます。前回の修正は PHP2Shell（8.5.12 / 8.4.27 / 8.3.36 / 8.2.35）を参照。
